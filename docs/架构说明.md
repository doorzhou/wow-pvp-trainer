# 架构说明

给未来的自己（或接手的人）看的。**先读这份，再改任何东西。**

---

## 为什么要有构建这一步

第一版是 6 个各自独立的单体 HTML，每个 135KB，CSS 和交互引擎各存 6 份。
改一个按钮样式要改 6 处，加第 7 个专精就变 7 处。目标是 **13 职业 40 专精**——这个形态撑不到。

现在的形态：

```
内容（每个专精一个文件）  →  构建  →  静态页 + 运行时数据
_build/content/*.js          node all.js       site/*.html
                                               site/data/specs/*.js
                                               site/data/quiz/*.js
```

三条硬约束决定了现在的样子：

1. **正文必须在 HTML 里，不能靠 JS 注入。** 站点的目的之一是被搜到，百度对 JS 渲染的支持很差。
   所以所有静态正文（通用手法、赛前速查、13 个职业对阵面板）在**构建期**就写进 HTML。
2. **题库不进首屏。** 300 道题里每页 40–56 道，约 50KB。点开「判断训练」那一刻才加载。
3. **样式和引擎只下载一次。** `core.css` / `app.js` / `skdb.js` 全站共用，浏览器缓存一次管所有页。

## 数据流

```
_build/content/<id>.js ──┬─→ 静态正文内联进 <id>.html      （爬虫读这个）
                         ├─→ site/data/specs/<id>.js       （决策器/分步器/天赋，随页加载）
                         └─→ site/data/quiz/<id>.js        （题库，点开才加载）

site/data/registry.js ───┬─→ index.html 的职业矩阵         （构建期渲染）
                         ├─→ 每页底部「换一个练」           （运行时渲染）
                         └─→ sitemap.xml
```

## 六个内容轴

每个训练器分六块，`registry.js` 里用 `st: [0,1,2,...]` 记完成度
（0=没有 1=部分 2=完成），首页每张卡下面的六个小格就是它。

| 轴 | 章节 | 来源 |
|---|---|---|
| 骨架 | s1 | content 的 sections.s1 + cond/verdicts |
| 手法 | s2 | content 的 fragments.general + steps |
| 对阵 | s3 | content 的 match |
| 天赋 | sTal | pages.js 里的 talent |
| 装备 | sGear | pages.js 里的 gear + app.js 里的全站通则 |
| 训练 | 训练页 | content 的 quiz |

**装备通则写在 `app.js` 的 `GEAR_COMMON` 里，全站共用**——货币、催化器、饰品解控位这些机制对所有专精一样，只写一遍。
每个专精自己的属性排序放 `pages.js` 的 `gear.stats`，没实测就留空，页面会显示「资料待补」和补法。

## 三条内容纪律

改内容的时候不要破：

**一、不编中文技能名。** 查 Wowhead 官方接口拿简体中文名。查不到就用英文原名并在页面上注明"官方中文名未核到"。
第一版就是靠猜译名翻过车——毒伤/影袭/秘密技艺全是编的，实际是刺骨/暗影之刃/影分身。

**二、文案只写信息，不写编辑方针。** 没有的内容标「待补充」，不解释为什么没有；不写界面说明书；不用第一人称表态。
判据：这句话删掉，读者会不会少知道一件事？不会就删。

**三、实测和推导分开写。** 首页有专门一段划这条线。
技能说明、天赋使用率、版本改动、梯队 = 有出处；判断框架、控制链结构、题目设计 = 编者推导。
**不写具体秒数和装等数字**——数值每次平衡都在动，写死了下个补丁就是错的，写相对关系。
